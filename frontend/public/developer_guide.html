1. Project Overview & Purpose

Valuevade is an Indian finance education platform targeting equity-research and financial-modelling careers. It was built to close the gap between what Indian colleges teach (exams) and what finance employers actually need (financial modelling, valuation, research, and interview skills).

What the platform offers

FeatureWhat it does
Course Curriculum21 modules · 239 sessions · video + notes + quiz + simulation per session
AI Mock Interview Sim5-round interview with J.P. Morgan, Goldman, Motilal etc. powered by Claude Haiku/Sonnet
NISM Mock ExamTimed MCQ certification exam (Series XV — Research Analyst), with score ring + per-question review
Pari (AI Tutor)In-context doubt chat (Claude Haiku) — paused during graded surfaces, daily quota cap
Gamified RewardsXP, streaks, badges, milestones, daily challenges, module constellation map
LinkedIn RewardsShare a milestone on LinkedIn → unlock a free resource (resume template, IB toolkit, etc.)
Free TrialUnauthenticated 5-round J.P. Morgan mock interview at /free-trial/:trialId
Study Planner3-mode planner (deadline / hours-per-day / hours-per-week) with trend chart + rebalance
Portfolio PagePublic shareable portfolio at /p/:slug with badges, skills, heatmap
Admin PanelFull CRUD for curriculum, videos, quizzes, simulations, rewards, users, payments, errors

Business model

One-time lifetime enrolment at ₹999 (Razorpay TEST MODE). Students get access to all 21 modules after payment. There is no subscription.

Request routing

The platform runs behind a Kubernetes ingress proxy. Any URL containing /api is forwarded to the FastAPI backend on port 8001. All other URLs go to the React frontend on port 3000. This means every backend endpoint must be prefixed with /api.

Key rule for new developers Never call localhost:8001 from the frontend. Always use process.env.REACT_APP_BACKEND_URL (e.g. https://mock-exam-mvp.preview.emergentagent.com). The proxy handles the internal forwarding.

Module registration pattern

The backend is split into 6 endpoint modules, all registered into a single APIRouter in server.py. Each module exports a register_*(api_router, deps) function. The deps dict injects shared helpers (Supabase getter, auth dependency, LLM key, etc.) so modules don't need to re-import from server.py.

# server.py (simplified)
from wave_endpoints import register_wave_endpoints
register_wave_endpoints(api_router, {
    "supabase_get":  _supabase_get,
    "supabase_post": _supabase_post,
    "get_supabase_user": _get_supabase_user,
    "ensure_admin":  _ensure_admin,
    ...
})

4. Backend — FastAPI

The backend is a single FastAPI application using uvicorn as the ASGI server. It talks to Supabase PostgreSQL via direct HTTP (PostgREST REST API) rather than a SQL driver — this avoids connection pooling complexity and works well with Supabase's built-in Row Level Security.

Supabase client pattern

All database reads/writes go through two thin wrappers defined in server.py:

def _supabase_get(path: str) -> list | dict:
    """HTTP GET to PostgREST. path is the table + filter, e.g.
       'profiles?id=eq.{uid}&select=*&limit=1'
    """

def _supabase_post(table: str, row: dict, prefer="return=representation"):
    """HTTP POST (INSERT). Returns the inserted row(s)."""

def _supabase_patch(path: str, patch: dict):
    """HTTP PATCH (UPDATE). path includes table + filter."""

def _supabase_delete(path: str):
    """HTTP DELETE. path includes table + filter."""

All calls use the SUPABASE_SERVICE_ROLE_KEY which bypasses Row Level Security — the application layer is responsible for enforcing access rules.

LLM cost tracking

Every LLM call goes through _bump_pari_cost(user_id, inr_amount) which writes to profiles.pari_total_cost_inr via a Supabase RPC. Token count is estimated as len(text) / 4. Claude Haiku pricing: ₹0.085 per 1K input tokens, ₹0.425 per 1K output tokens.

# Cost constants (server.py)
_INR_PER_IN  = (1.0 / 1_000_000) * 85   # Haiku input  ~$1/M tokens × ₹85
_INR_PER_OUT = (5.0 / 1_000_000) * 85   # Haiku output ~$5/M tokens × ₹85

# When pari_total_cost_inr >= 500 the Pari endpoints return HTTP 402
# with detail.reason = 'pari_cost_limit_reached'

Rewards engine

Students earn a reward (resume template, IB toolkit, etc.) after completing a module or capstone by sharing a LinkedIn post. The flow:

Admin creates reward → links it to module_complete or capstone_complete trigger ↓ Student completes trigger condition ↓ GET /api/rewards/eligible ← checks user_modules completion ↓ Student pastes LinkedIn URL → POST /api/rewards/claim ↓ _verify_linkedin_post_content() fetches URL with bot UA └─ If verified=true → mark claim linkedin_post_verified=true └─ If unreachable → allow claim, mark verified=false (admin reviews) └─ If SSRF redirect → block (SafeRH handler) ↓ GET /api/rewards/{id}/download ← issues signed Supabase Storage URL

The full 5-round interview simulator for paid/enrolled students. Uses Claude Haiku for most rounds, Claude Sonnet for the final decision report (more expensive, more nuanced output).

4e. guest_interview_sim_endpoints.py — Free Trial

Identical 5-round flow but for anonymous (no-auth) users. No database writes — all state lives in the browser's localStorage. Rate limited:

  • Per trial-id: 40 LLM calls max (prevents a single trial from burning the key)
  • Per IP: 120 LLM calls max (prevents rotating trial IDs to bypass per-trial cap)
Stateless by design. The backend doesn't store conversation state — the frontend sends the full stage_data (all previous turns) with every request. This means a backend restart during a trial is safe — the user just needs to re-send their last turn.

5c. Pages & Components

Learning flow — session phases

Every session has 3 phases that must be completed in order:

/session/:id/start ← intro + phase overview ↓ /session/:id/notes ← video player + flashcard notes (NotesPage) ↓ /session/:id/notes/complete ← confirmation ↓ /session/:id/quiz/start ← quiz rules ↓ /session/:id/quiz ← MCQ quiz (QuizPage) ↓ /session/:id/quiz/complete ← score + feedback ↓ /session/:id/simulation/start ← simulation rules ↓ /session/:id/simulation ← Excel / Decision / Book sim (SimulationPage) ↓ /session/:id/complete ← XP gain, milestone overlay, summary card

7. Authentication

The app uses Supabase Auth — email/password only. There is no Google/social login. Auth lives entirely in the Supabase cloud; the backend never stores passwords.

Frontend auth flow

1. User submits login form → supabase.auth.signInWithPassword({email, password}) 2. Supabase returns { session: { access_token, refresh_token }, user } 3. AuthContext stores session in state. supabase client auto-persists to localStorage. 4. On any API call: Authorization: Bearer {session.access_token} 5. Token refreshes automatically via supabase.auth.onAuthStateChange() 6. On logout: supabase.auth.signOut() → clears localStorage

Backend auth flow

1. Request arrives with Authorization: Bearer {jwt} 2. _get_supabase_user() calls GET /auth/v1/user with that token 3. Supabase validates the JWT and returns the user object 4. If token expired/invalid → Supabase returns 401 → we raise HTTP 401 5. user dict is passed to the route handler

Admin auth

The admin panel at /admin-panel is a ProtectedRoute — any Supabase user can load the page, but every admin API call (e.g. GET /api/admin/users) calls _ensure_admin(user) which checks that user.email in ADMIN_ALLOWED_EMAILS. The only admin email is info@valuevade.com.

There is also a legacy JWT-based admin at /referral (the old waitlist admin). It uses ADMIN_EMAIL, ADMIN_PASSWORD, ADMIN_SECRET from backend/.env and is separate from the Supabase admin.

12. Security Model

Authentication enforced everywhere

  • All non-public backend routes use Depends(_get_supabase_user) to verify the Supabase JWT.
  • All admin routes additionally call _ensure_admin(user).
  • Guest endpoints (free trial / preview sessions) have no auth but are rate-limited.

Razorpay webhook security

The webhook at POST /api/payments/webhook verifies every request using HMAC-SHA256 with RAZORPAY_WEBHOOK_SECRET. If the secret is not set in .env, the endpoint returns HTTP 503 (hard reject). This prevents payment forgery.

Trial ownership

The PATCH /api/free-trial/{id} endpoint requires the caller to provide the email used to start the trial. Mismatched email → HTTP 403. This prevents one user from corrupting another user's trial results.

SSRF protection (LinkedIn rewards)

When verifying a LinkedIn share URL, the _SafeRH custom redirect handler only allows HTTP redirects to linkedin.com or lnkd.in. Any redirect to another host (including internal IP addresses) is blocked before a socket is opened.

18. Common Patterns & Conventions

How to add a new API endpoint

# 1. Decide which module it belongs to:
#    - Core/Pari/Gamification/Portfolio → server.py
#    - Curriculum/Admin/Rewards         → wave_endpoints.py
#    - Payments                         → payment_endpoints.py
#    - Interview sim                    → interview_sim_endpoints.py

# 2. Inside the register_*() function, define the route:
@api_router.get("/my-new-endpoint")
async def my_endpoint(user=Depends(_get_supabase_user)):
    # Always validate auth first
    data = _supabase_get("some_table?user_id=eq." + _urlparse.quote(user["id"]))
    return {"result": data}

# 3. All routes MUST be inside register_*() — not at module level.
#    (So the api_router is available as a closure variable.)

# 4. Always prefix with /api when calling from the frontend:
#    fetch(`${REACT_APP_BACKEND_URL}/api/my-new-endpoint`, ...)

How to add a new frontend page

# 1. Create the component:
//  /app/frontend/src/components/MyNewPage.jsx
export default function MyNewPage() {

  // ...
}

# 2. Add to App.js:
import MyNewPage from './components/MyNewPage';
// Inside <Routes>:
<Route path="/my-new-page" element={<ProtectedRoute><MyNewPage /></ProtectedRoute>} />

# 3. Add a link in Sidebar.jsx if it's a learning-flow page.

How to make an authenticated API call from the frontend

import { useAuth } from '../contexts/AuthContext';

function MyComponent() {
  const { session } = useAuth();
  const API = process.env.REACT_APP_BACKEND_URL;

  const fetchData = async () => {
    const res = await fetch(`${API}/api/some-endpoint`, {
      headers: {
        'Content-Type': 'application/json',
        'Authorization': `Bearer ${session.access_token}`,
      },
    });
    if (!res.ok) throw new Error(await res.text());
    return res.json();
  };
}

Important "gotchas" for junior developers

1. The mongo URL in .env is unused. All data is in Supabase. MONGO_URL and DB_NAME are legacy leftovers. Ignore them.
2. session.interview_completed is not used. The interview phase was disabled (cost reduction). The allDone() function only checks notes + quiz + simulation. Do not add logic that depends on interview_completed.
3. Don't use npm — use yarn. The frontend uses yarn for package management. Running npm install will create a conflicting package-lock.json and can break the build.
4. Supabase ObjectIds vs UUIDs. All IDs are UUID v4 strings. Never pass them as integers. Always URL-encode them before including in PostgREST filter strings (use urllib.parse.quote(id)).
5. Hot reload on code, but supervisor restart on .env. Changing Python or JSX files triggers automatic hot-reload. Changing .env files or installing new packages requires sudo supervisorctl restart backend (or frontend).
Where to look when something breaks:
Backend crash: tail -n 100 /var/log/supervisor/backend.err.log
Frontend crash: check the browser console (F12)
Supabase query failing: add print() in the backend and re-run the request
Auth issue: verify the Bearer token hasn't expired by calling GET /api/health with it
